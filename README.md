# ROS 2 Network Security Lab with SROS2

## Objective

This lab examines what an attacker on a ROS 2 network can read and send with default settings, and what changes after SROS2 is enabled. It is a learning exercise on hardware owned by the author and does not describe any real product or deployment.

## Environment

- Docker
- Official `ros:lyrical` image (ROS 2 Lyrical Luth)
- Fast DDS (`rmw_fastrtps_cpp`)
- One Docker network named `rosnet`

## Setup

Build the image from the Dockerfile in this repository and create the network:

```
docker build -t ros-sec-lab .
docker network create rosnet
mkdir -p keys captures
```

The `keys/` and `captures/` directories are intentionally not part of the repository. They are listed in `.gitignore` and must be generated by following the steps below.

## Procedure

### Stage 1: Baseline with no security

Start the talker and the listener in separate terminals:

```
docker run --rm -it --name talker --network rosnet ros-sec-lab \
  ros2 run demo_nodes_cpp talker

docker run --rm -it --name listener --network rosnet ros-sec-lab \
  ros2 run demo_nodes_py listener
```

Capture 30 seconds of UDP traffic from inside the talker's network namespace:

```
docker run --rm --network container:talker -v "$PWD/captures:/captures" ros-sec-lab \
  timeout 30 tcpdump -i eth0 -U -w /captures/baseline.pcap udp
```

Inspect the capture:

```
docker run --rm -v "$PWD/captures:/captures" ros-sec-lab tcpdump -nr /captures/baseline.pcap | head -25
strings captures/baseline.pcap | grep "Hello World" | head
strings captures/baseline.pcap | grep -c "Hello World"
strings captures/baseline.pcap | grep -o 'Hello World: [0-9]*' | sort -u | wc -l
```

Start the attacker container, a plain shell on the same network with no keys:

```
docker run --rm -it --name attacker --network rosnet ros-sec-lab bash
```

Inside the attacker shell, the topics are listed and a message is published to `/chatter`:

```
ros2 topic list --no-daemon --spin-time 3
ros2 topic pub --once /chatter std_msgs/msg/String "{data: 'injected by attacker'}"
```

The topic list includes `/chatter`, and the injected message appears in the listener's output between the talker's own messages.

### Stage 2: SROS2 enabled

Create the keystore and one enclave per node:

```
docker run --rm -v "$PWD/keys:/keys" ros-sec-lab bash -c "cd /keys && ros2 security create_keystore keystore && ros2 security create_enclave keystore /talker_listener/talker && ros2 security create_enclave keystore /talker_listener/listener"
```

Run the talker with security enforced:

```
docker run --rm -it --name talker --network rosnet -v "$PWD/keys:/keys:ro" \
  -e ROS_SECURITY_KEYSTORE=/keys/keystore -e ROS_SECURITY_ENABLE=true -e ROS_SECURITY_STRATEGY=Enforce \
  ros-sec-lab ros2 run demo_nodes_cpp talker --ros-args --enclave /talker_listener/talker
```

Run the listener the same way, with `demo_nodes_py listener` and `--enclave /talker_listener/listener`.

Capture and inspect the secure traffic:

```
docker run --rm --network container:talker -v "$PWD/captures:/captures" ros-sec-lab \
  timeout 30 tcpdump -i eth0 -U -w /captures/secure.pcap udp
strings captures/secure.pcap | grep -c "Hello World"
docker run --rm -v "$PWD/captures:/captures" ros-sec-lab tcpdump -nr /captures/secure.pcap | head -25
```

Start the attacker again with the same command as in Stage 1 and run the same two commands. No keystore is mounted and no `ROS_SECURITY_*` variables are set. The topic list shows only `/parameter_events` and `/rosout`, and the publish command keeps printing `Waiting for at least 1 matching subscription(s)...` while the listener receives nothing extra.

### Stage 3: Access control

Generate permissions for both enclaves from the sample policy shipped with sros2:

```
docker run --rm -v "$PWD/keys:/keys" ros-sec-lab bash -c "cd /keys && ros2 security create_permission keystore /talker_listener/talker /opt/sros2/sros2/test/policies/sample.policy.xml && ros2 security create_permission keystore /talker_listener/listener /opt/sros2/sros2/test/policies/sample.policy.xml"
```

Before applying the policy, a listener remapped to a different topic is started with valid keys:

```
docker run --rm -it --name listener --network rosnet -v "$PWD/keys:/keys:ro" \
  -e ROS_SECURITY_KEYSTORE=/keys/keystore -e ROS_SECURITY_ENABLE=true -e ROS_SECURITY_STRATEGY=Enforce \
  ros-sec-lab ros2 run demo_nodes_py listener --ros-args --enclave /talker_listener/listener \
  --remap chatter:=not_chatter
```

The listener starts and waits. After the policy is applied, the same command is run again. It fails with `rt/not_chatter topic not found in allow rule` and exits. The unmodified listener (no `--remap`) still receives the talker's messages.

## Results

| Measurement | Baseline | SROS2 |
|---|---|---|
| Packets in 30 s capture | 91 | 110 |
| Readable `Hello World` messages | 29 | 0 |
| Attacker sees `/chatter` | Yes | No |
| Attacker's message reaches the listener | Yes | No |

The remapped listener starts before the policy is applied and is refused after it. Encrypted traffic still reveals which addresses and ports communicate, the packet rate, and packet sizes. The extra packets and larger sizes in the secure capture were not decoded.

## Limitations

- The whole keystore, including the CA private key, was mounted into every container.
- Other attack surfaces such as physical access, cloud, updates, and wireless are out of scope.
- Key management at fleet scale was not tested.
- The lab used one host and one middleware.
